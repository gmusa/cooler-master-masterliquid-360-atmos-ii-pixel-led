# Pixel dashboard — preview, bounded live and user service

Python 3.11+ and [uv](https://docs.astral.sh/uv/): run `uv sync` in this checkout, then `uv run pixel-dashboard preview --config examples/config.toml --frames 20 --output preview.gif`. Alternatively, when Pillow is already installed: `PYTHONPATH=src python -m pixel_dashboard preview --config examples/config.toml --frames 20 --output preview.gif`. Preview is bounded to 1–300 frames, uses synthetic sample readings, and never opens USB or probes sensors. Output path is caller-selected. `--locked` previews the locked playlist; it does not query or configure Noctalia.

TOML requires `[normal]` and `[locked]`, each with a nonempty ordered `[[...widgets]]` list. Names: `clock`, `date`, `cpu`, `gpu`, `animation`. Options `duration` (seconds, >0 to 3600), `brightness` (0–100), `rotation` (0, 90, 180 or 270 degrees), `fps` (0.01 to 100, GIF timing resolution 10 ms), `mask` (boolean) inherit from `[defaults]` to environment to widget; unknown fields are errors. `ConfigStore.poll()` checks file mtime and size synchronously; changed files are validated and swapped only on success, retaining the last good configuration on errors. `.error` holds the latest diagnostic. The bounded preview polls once per frame without threads. Live mode polls config synchronously and reconciles Noctalia IPC lock status every 0.25 seconds, including between slow frames; a failed status poll selects locked even after a prior unlocked reply; a later valid unlocked reply restores the normal playlist. Each transition resets the selected playlist epoch. Service installation is a separate parent-operated step; Noctalia hooks are not required. Preview uses a logical clock starting at zero: each frame selects the widget owning its elapsed time in the ordered, repeating playlist, then advances by that widget's `1/fps` seconds. `--trace` prints frame time and widget. Brightness, rotation and the exact 32×32 LED topology mask are applied to the image; GIF timing is quantized to 10 ms. The non-LED preview corner (0,0) carries a transparent per-frame marker so visually identical frames remain distinct in the GIF. Mask row bounds derive from cm-pixel 0.1.0 `cmpixel/layout.json` (copyright 2026 Feiko, MIT); its license is included at `src/pixel_dashboard/LICENSE-cmpixel.txt`.

To choose a cm-pixel library effect for an animation widget, add this valid TOML inside a playlist:

```toml
[[normal.widgets]]
name = "animation"
animation = "plasma"
```

Choices: `plasma`, `rainbow`, `swirl`, `ripple`, `breathe`, `sparkle`, `fire`, `starfield`, `tunnel`, `metaballs`, `matrix`, `fireworks`, `aurora`, `comet`, `pinwheel`, `bounce`, `interference`, `twinkle`, `rubik`. The selector is valid only for animation widgets; selected library effects retain their intrinsic RGB colors. Omitting it preserves the moving dot, colored with Noctalia secondary when a palette is provided. Each selected effect continues frame by frame within its playlist entry and restarts on entry boundary, playlist wrap, lock transition or valid configuration reload. No speed selector is provided.

Noctalia v5.6 integration: the active host scheme was reported as `custom rose2` (resolved `dark`); actual hex colors come from the generated template, not Noctalia's internal JSON. Copy/merge `integrations/noctalia/pixel-dashboard.toml` into your own v5 configuration only after replacing both placeholder paths, then validate with `noctalia config validate <your-config>`. The template at `integrations/noctalia/palette.toml` produces three strict hex roles. It darkens the active scheme's `primary`, `secondary`, and `on_surface` by 18 HSL lightness points: values stay vivid while identity labels, clock, and date retain a lighter rose tint rather than appearing blue-white on the LEDs; it does not set device brightness. Regenerate the output through Noctalia after changing the template. Pass its chosen output as `--palette /chosen/path/pixel-dashboard-palette.toml` to preview or live. A missing file keeps original widget colors; malformed initial output is rejected before preview output or USB opening, and later invalid writes retain last-good colors. No installation, hook or external config write is performed by this project. Live status uses read-only `noctalia msg status`; it never writes Noctalia settings.

Sensor readers are read-only subprocess adapters: `sensors -j` k10temp Tctl and `nvidia-smi` RTX 5070 temperature/utilization. Each CPU/GPU entry alternates one large temperature reading (first half) with one large utilization percentage (second half) within that entry's configured duration; a small CPU/GPU label stays visible. Missing measurements show `--`, not fabricated readings. With a Noctalia palette, the temperature uses `primary`, utilization uses `secondary`, and the label uses `on_surface`; without one, the value uses the widget's accent color. Preview's synthetic CPU sample has temperature only (no CPU usage), while its synthetic GPU sample has temperature and utilization. Partial/unavailable live readings remain unset. NVIDIA's `fan.speed` is a percentage, not RPM, so fan RPM remains unavailable. CPU usage is computed from successive `/proc/stat` aggregate deltas; the initial sample is unavailable. Run `pixel-dashboard live --config examples/config.toml --duration 10` only when explicitly intending USB output. Live mode selects the `hidraw` module inside the process before opening cm-pixel's PixelDisplay, opens once, applies the same widget options as preview, and closes once at exit. It does not clear the screen on exit: the last frame remains until replaced by another owner. Device absence or permission failure returns a readable error and nonzero status; do not run as root to bypass permissions. Live does not write configuration files. The duration is bounded to 3600 seconds; playlist selection, frame pacing and deadline use a monotonic clock, while live clock/date widgets receive the current wall-clock timestamp. Preview retains its logical clock starting at zero. The live loop sleeps until the next frame, status poll or deadline. A rejected configuration opens no device.

Persistent mode: `pixel-dashboard serve --config /path/config.toml --palette /path/palette.toml` uses the same single-owner, paced USB loop as live, runs until SIGTERM (systemd) or Ctrl-C, and closes the display on exit. A bad reload retains the last valid frames and reports once per distinct failed file revision to stderr (the user journal), with a best-effort bounded `notify-send` desktop alert. After recovery, later bad revisions are reported again. Initial invalid config rejects before opening USB. Optional palette continues to retain last-good colors. The user unit is `integrations/systemd/pixel-dashboard.service`: restart on failure, start with the user default target, no root shell. It assumes this checkout at `%h/cm-pixel`, an installed `.venv` with the CLI and USB backend, and a validated user config at `%h/.config/pixel-dashboard/config.toml` with conservative brightness. Install dependencies offline using `uv venv .venv` and `uv pip install --offline --python .venv/bin/python .`; validate the unit with `systemd-analyze verify integrations/systemd/pixel-dashboard.service`. After checking `/dev/hidraw5` has no other owner, install the unit in `~/.config/systemd/user/pixel-dashboard.service`, run `systemctl --user daemon-reload` and `systemctl --user enable --now pixel-dashboard.service`. Inspect with `systemctl --user status pixel-dashboard.service` or `journalctl --user -u pixel-dashboard.service`. Stop it with `systemctl --user stop pixel-dashboard.service` before any manual `live` or `cm-pixel` USB run: the program does not enforce cross-process device exclusivity. Systemd sends SIGTERM on stop and restarts a crash, but not a deliberate stop.
